## 데이터 저장 및 동기화

---

Jade의 데이터 저장 핵심 로직은 아래와 같이 정리된다.

- 모든 데이터의 원본은 **로컬 Markdown 파일** (페이지)이다.
  - Markdown 파일의 프론트매터에 **고유한 UUID v4**를 기록한다.
  - 논리적인 의미를 지니는 폴더는 사용하지 않으나, 최적화와 버전 관리 효율성을 위해 UUID v4 기반 **분할 디렉토리** (8/4/4/4) 폴더 구조를 지닌다.
  - 파일명은 UUID v4의 마지막 12자리로 고정된다.
- 데이터의 인덱스에 한해 **외부 SQLite DB**를 사용한다.
  - 모든 블록에 **UUID v4**를 부여하여 저장한다. 콘텐츠 해시와 정규화 해시 두 종류를 모두 사용한다.
  - `parent_id`, `prev_id`, `next_id` 필드를 통해 **이중 연결 리스트** 구조로 블록 간의 관계를 저장한다.
  - 분수 인덱싱을 활용해 재정렬 시 비용을 줄인다.
  - 내용의 해시와 콘텐츠 전체를 저장하여 FTS5 검색에 활용한다.
- 수정 사항의 **추적**은 CRDT를 응용하여 해결한다.
  - 자체 편집기 내에서의 모든 수정 사항은 **작업 로그**로 기록한다.
  - 외부 편집기로 인한 변경은 **Diff 알고리즘** (유사도 분석)을 통해 기존 UUID와 재매칭한다.
  - 본문 (`Yjs`)와 프론트매터 (`JSON CRDT`)를 구분하여 **구역별로 별도의 CRDT**를 적용한다.
  - 파일의 삭제 시 물리적 삭제 대신 **삭제 마커 처리** 후 앱 내부에서 휴지통에서만 노출 시킨다. 모든 기기에서의 동기화가 확인된 후에 물리적으로 삭제한다.
- 동기화 흐름은 **저장**, **전송**, **갱신**, **배포**로 나뉜다.
  - **저장**: 로컬에서 변경 사항 발생 시 SQLite의 미동기화 큐에 적재한다.
  - **전송**: 서버와 연결될 시 CRDT 변경 이력 바이너리를 중앙 서버로 전송한다.
  - **갱신**: 전송된 변경 이력에 따라 중앙 서버 (`PostgreSQL + Object Storage`) 스냅샷을 업데이트 한다.
  - **배포**: WebSocket을 통해 CRDT 변경 이력을 각 클라이언트로 배포한다.
  - 이 모든 과정에는 E2EE (종단간 암호화)가 적용된다.

## 문법

---

Jade의 문법은 이하 Maxdown이라 칭한다.

### 규칙

---

Maxdown의 모든 문법은 아래와 같은 규칙을 준수해야 한다.

1. Maxdown은 GFM으로부터의 단방향 변환 시 **완전히 호환**되어야 한다.
2. Maxdown에서 GFM으로의 역방향 변환 시 **기존에 작성한 문장이 보존**되어야 하고, Maxdown의 문법은 순수 텍스트로 처리될 지 언정 **다른 문법으로 잘못 해석되면 안 된다.** 이는 문서의 손상이 아닌 기능적 축소로 정의된다.
3. Maxdown으로 작성된 문서는 **기계가 읽는 공간인** 프론트매터와, **사람이 읽는 공간인** 본문이 철저히 구분되어야 한다.
4. Maxdown은 사용자가 본문의 구조적인 의미 전달을 위하여 HTML 태그 / CSS 문법을 사용하는 행위를 최소화하여도 문서가 원활히 작성될 수 있어야 한다.
5. Maxdown의 본질은 **GFM Superset**으로 남아야 한다. 단, GFM을 제외한 타 Markdown 확장 문법과의 호환성은 설계 단계에서 **고려하지 않았음**을 명시한다.
6. Maxdown의 확장 형식은 Markdown의 핵심적인 표현 철학 두 가지와 반대되면 안 된다. Markdown의 핵심적인 표현 철학이란, **암시적인 토큰형 문법**을 사용해 순수 텍스트 형태에서의 가독성을 확보해야 하며, 복수의 개수로 토큰을 구성할 시 진입 장벽과 판독성을 위하여 **서로 다른 기호를 함께 사용하면 안 된다**는 점이 있다.

### 최소 단위

---

Maxdown 문서는 모두 노드로 정의되며, 아래와 같은 단위로 구성된다.

- 문서의 최소 **편집** 단위는 **마크**이다. 마크는 언제나 블록에 소속되어야 한다.
- 문서의 최소 **의미** 단위는 **블록**이다. 블록의 구분은 Remark 라이브러리의 AST 구조를 따른다.
- 문서는 **페이지**라는 최소 **저장** 단위로 추상화 되어 표현된다. 페이지는 모든 노드를 포함하는 루트 노드이다. 페이지의 하위 요소로 블록을 생략하고 마크가 존재하는 것은 불가능하다.

### 기본 구조

---

- **줄바꿈** (`<br>`, `break Node`)는 한 개의 개행 문자로 입력한다.
- **단락** (`<p>`, `paragraph Node`)는 두 개의 개행 문자, 즉 하나 이상의 비어있는 줄로 입력한다.
- **이스케이프**는 단일 역슬래시 (`\`)를 사용한다.
- **리터럴 역슬래시**는 이중 역슬래시 (`\\`)로 입력한다.
- HTML 주석을 대신하기 위한 **Maxdown 주석**은 물음표 두 개, 그리고 주석 구문 사이의 양쪽 공백으로 사용한다. 주석 처리된 텍스트 / 단락은 최종 렌더링 단계에서 완전히 생략된다.
  - 사용 예시: `?? Comment ??`
- **단락 형태의 주석**은 물음표 세 개로 하나 이상의 단락을 감싸 입력한다.
  - 사용 예시:
  ```
  ???
  Paragraph
  ???
  ```
- 서로 다른 종류의 문법을 결합하는 문법의 중첩 사용은 **허용**된다. 결합 순서나 중복 횟수의 제한은 없으나, 언제나 **바깥쪽 토큰의 문법이 안쪽 토큰의 문법을 포함**하는 구조로 작용한다. 이는 파싱 우선 순위에 대한 규칙 역할 또한 수행함을 명시한다.

### 문법 종류

---

#### 인라인 마크

---

**볼드**

```
**Text**
__Text__
```

---

**이탤릭**

```
*Text*
_Text_
```

---

**취소선**

```
~~Text~~
```

---

**밑줄**

```
~Text~
```

왜 필요한가: 초기 CommonMark에서 링크와의 혼동 가능성과 HTML로의 대체 가능성 때문에 배제됐으나, 10년이 넘게 흐른 현재는 밑줄 이외에도 링크 식별 요소가 다양해졌고 HTML 사용을 최소화했기에
왜 이 문법인가: 따지고 보면 순수 GFM 표준 사양에는 단일 물결표를 사용하는 문법이 없고, 취소선과 겹치는 토큰을 쓰는 것에 대해서는 이미 볼드와 이탤릭도 같은 토큰을 사용 중이며, Pandoc과 Typora 등 타 확장 문법에서 다른 의미로 사용 중인 검증된 토큰이기에

---

**위 첨자**

```
^^Text^^
```

왜 필요한가: LaTeX 수식이라는 외부 문법 없이 순수 Markdown으로 표현 가능한 진입 장벽 낮은 위 첨자 문법이 필요했기에
왜 이 문법인가: 캐럿 기호가 상승 방향을 시각적으로 연상시키기에

---

**아래 첨자**

```
,,Text,,
```

왜 필요한가: 위 첨자와 같은 이유로 아래 첨자 문법이 필요했기에
왜 이 문법인가: 연속 쉼표는 자연어에서 거의 사용되지 않고 다른 글자들보다 높이가 낮아 아래 방향을 시각적으로 연상시키기에

---

**리터럴**

```
""Text""
```

왜 필요한가: 리터럴 문자열을 표현할 방법이 복수의 문자를 처리할 수 없는 이스케이프, 그리고 모노스페이스 글꼴 + 특수 스타일로 표시되는 인라인 코드 / 코드 블록 밖에 없기에
왜 이 문법인가: 이중 따옴표는 실제 문서에서 사용 사례가 매우 적으며, 안정적으로 쓸 수 있고 시각적으로 다른 기호와 혼동이 없는 토큰이 큰따옴표였기에

**하이라이트**

```
==ColorCode | Text==
```

사용 방법:

- `ColorCode` ==> 용도별 Color Preset, CSS 색상명, CSS 변수명, 6자리 일반 HexCode, 3자리 단축 HexCode
  - 쉼표로 두 코드를 구분하여 라이트 테마 / 다크 테마 구분 가능
    왜 필요한가: 일반 Markdown에서는 색상 지정은 HTML / CSS로 역할을 넘기지만, Maxdown은 범용 포맷이 아닌 Jade라는 PKM 앱의 전용 포맷이며, PKM에서는 하이라이트 색상 지정의 수요가 많기에
    왜 이 문법인가: 기존 확장 문법 / PKM의 하이라이트 문법의 토큰을 재활용할 수 있기에
